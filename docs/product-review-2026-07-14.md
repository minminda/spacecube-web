## 1. 사용자 경험 — QR → 공간 → Episode → 취향 점수 → 방명록 → 추천 → 아카이브

### QR 진입
- **좋은 점**: `/c/[code]` → Cube Unlock 4초 애니메이션 → 공간 페이지로 이어지는 흐름이 "체크인"이 아니라 "의식(ritual)"으로 설계돼 있음. 큐브별 스캔 로그(`cubeId`/`userAgent`/`referrer`/`locale`)까지 남겨 계측 품질이 높음.
- **부족한 점**: QR을 잘못 인식하거나(각도/조명/인쇄 품질) 큐브가 아직 미등록/비활성 상태일 때의 안내는 있지만, 오프라인에서 "이 QR이 왜 안 되는지" 사용자가 알 방법이 없음(문의처 없음).
- **UX가 끊기는 부분**: 없음(가장 매끄러운 구간).
- **우선순위**: 낮음(현재도 충분).

### 공간 페이지
- **좋은 점**: 운영자 한마디, Episode 잠금 상태, 저장(찜) 버튼, 다국어 스위처가 한 화면에 자연스럽게 배치됨. `SHOW_REACTION_BOARD`/레거시 `anonymousReactions` 등 죽은 분기가 이미 최근 리팩터링으로 정리됨.
- **부족한 점**: "기록하고 흔적 열기" CTA 하나만 있어, 재방문자에게도 첫 방문자와 동일한 문구가 보임(예: "3번째 방문이시군요" 같은 환영 톤이 없음 — 이건 `/record`에서만 나옴, 공간 페이지 자체엔 없음).
- **개선 아이디어**: 재방문자에게 "지난번 이후 새 이야기 N개" 같은 요약을 공간 페이지 진입 즉시 보여주면(Episode 섹션 배너가 이미 있긴 하지만) 더 즉각적일 것.
- **우선순위**: 낮음(P2, 있으면 좋음 수준).

### Episode
- **좋은 점**: 방문 횟수로 잠금 해제되는 구조가 "다시 오고 싶다"는 동기를 억지스럽지 않게 만듦. 다음 이야기 "예정" 카드(placeholder)로 콘텐츠가 없어도 기대감을 유지.
- **부족한 점**: **Episode는 100% 운영자가 수동으로 써야 함.** 자동 생성/템플릿/AI 초안 같은 보조 도구가 전혀 없어, 공간이 늘어날수록 콘텐츠 공급이 병목이 됨. 또한 에피소드가 2~3개뿐인 공간은 신규 방문자가 금방 "다 봤다"는 상태에 도달 — 그 다음 재방문 동기가 약해짐(방명록 외엔 없음).
- **UX가 끊기는 부분**: Episode 목록에 링크된 이전/다음 에피소드 제목은 다국어 미지원(i18n 메모에 이미 스코프 아웃으로 기록됨) — 외국어 사용자가 마지막에 한국어를 다시 만남.
- **없어도 되는 기능**: 없음(핵심 리텐션 장치).
- **우선순위**: **P1** — 콘텐츠 공급 병목은 사업 확장 시 가장 먼저 부딪힐 문제.

### 취향 점수 (기록)
- **좋은 점**: 1~5점 단일 질문으로 마찰을 최소화한 선택은 옳음(과거 태그 2개 선택 방식보다 가볍다는 걸 이미 검증하고 전환한 이력이 있음).
- **부족한 점**: **이 단계에 자유 텍스트(메모)가 전혀 없음.** `Record.memo` 필드는 스키마에 있지만 현재 `RecordForm`은 점수만 전송함. "이 공간에 대한 나의 기록"이 결국 텍스트로 남는 곳은 방명록(공개)뿐이라, "나만의 기록"과 "남에게 보이는 흔적"이 구분되지 않음. 아카이브의 기록 상세 페이지(`archive/[recordId]`)도 점수·메모 없이 공간명/날짜/삭제 버튼뿐이라 존재 이유가 희미함.
- **개선 아이디어**: 점수 뒤에 "왜 이 점수를 줬는지" 짧은 비공개 메모 한 줄만 추가해도 아카이브가 훨씬 개인적인 기록물이 됨.
- **우선순위**: **P1** — 아카이브 가치와 직결.

### 방명록
- **좋은 점**: 무한 캔버스 + 충돌 방지 + 방문당 1흔적 정책이 최근 리팩터링으로 매우 정교해짐. 더미 데이터 제거 후 빈 상태 문구까지 갖춰짐.
- **부족한 점**: 아래 5번 섹션에서 상세.
- **UX가 끊기는 부분**: 없음.

### 추천
- **가장 큰 구조적 문제**: 추천/취향 업데이트 피드백(`PostSubmitReward`)은 **방명록 포스트잇을 실제로 작성해야만** 뜸. 기록(취향 점수)만 남기고 방명록은 안 쓰기로 한 사용자는 그 방문에서 추천을 아예 못 봄. 사용자 흐름도의 "추천" 단계가 조건부로 스킵될 수 있다는 뜻.

- **우선순위**: **P0** — 흐름도 자체가 약속하는 경험이 조건부로 깨짐.

## 2. 운영자 경험

**가정**: 공간에 큐브를 설치하고 한 달을 운영.

- **운영자가 궁금할 데이터**: "이번 달 몇 명이 왔고, 몇 명이 다시 왔는지", "방명록에 뭐라고 썼는지", "다들 이 공간을 몇 점으로 평가했는지" — 이건 `/operator`에 이미 다 있음(리팩터링으로 진입 메뉴까지 생김). 잘 만들어진 부분.
- **운영자가 자주 사용할 기능**: 다음 회차 질문 준비(`NextGuestbookPrep`), 이전 방명록 열람 — 둘 다 실사용 동선에 맞게 설계됨.
- **운영자가 귀찮아할 부분**:
  - **월간 리포트가 자동으로 안 옴.** 생성 버튼을 관리자가 눌러야 하고(`/owner/[id]/report-settings`), Cron 자체도 `vercel.json`이 없어 실제 스케줄이 안 걸려 있음(메모에 기록된 기존 갭). 운영자는 리포트가 있는지조차 매달 스스로 확인하러 와야 함 — 반대여야 함(리포트가 운영자를 찾아가야 함).
  - 대기 등록(Waitlist)이 이름+연락처 리스트일 뿐, 운영자가 "누구를 불렀는지/안 불렀는지" 상태 관리가 `CALLED` 상태값 외엔 부실.
- **운영자가 이해하기 어려운 부분**: `GuestbookSession`의 DRAFT→ACTIVE→ARCHIVED 개념 자체가 "방명록 회차"라는 새로운 멘탈모델을 요구함. 처음 쓰는 운영자는 "왜 예전 글이 안 보이지"에서 아카이브 개념을 배워야 함 — 온보딩 문구가 필요.
- **없는 기능(철학에 맞는 선에서)**:
  - 월간 리포트 알림(이메일/문자 실제 발송) — 스키마엔 `operatorNotifyEmail`/`operatorNotifyPhone` 필드까지 있는데 실제 발송 로직이 없음(cron 응답에 로그만 남음). 이건 SNS성 기능이 아니라 "내가 돈 내는 이유"에 직결되는 핵심 결여.
  - 방명록 신고/숨김 — 운영자가 부적절한 글을 발견해도 삭제 권한이 없음(작성자 본인만 삭제 가능). 오프라인 공간 특성상 "내 가게에 걸린 글"을 운영자가 통제 못 하는 건 실사용 리스크.

## 3. 관리자 경험

- **공간 관리**: CRUD·이미지 포지셔닝·공개/비공개 토글 모두 갖춰짐. 다만 신규 공간 생성 시 방명록 ACTIVE 세션이 자동으로 안 만들어짐(운영자 메모에 기록된 기존 갭) — 공간을 10곳 늘릴 때마다 관리자가 매번 "새 방명록 시작"을 잊지 않고 눌러야 함. 자동화할 가치가 있음.
- **콘텐츠 관리**: Episode/Scene 에디터는 있지만 초안 작성 보조가 전혀 없음(1번 섹션과 동일 문제).
- **번역 관리**: 구조는 탄탄하지만(fallback 체인, 중복 호출 방지) **실제 OpenAI 키로 한 번도 검증되지 않음**(i18n 메모에 명시) — 운영 투입 전 반드시 1회 실사용 검증 필요.
- **Cube 관리**: 최근 리팩터링으로 QR 체계가 하나로 통합돼 깔끔해짐. 다만 큐브 10개를 오프라인에 붙이고 나서 "어느 큐브가 어느 공간에 붙었는지" 실물과 매칭하는 절차가 전산엔 있어도 물리적으론 사람이 기억해야 함 — 인쇄 시트에 QR과 함께 공간명을 인쇄하는지 확인 필요.
- **KPI 관리**: 7번 섹션에서 상세.
- **운영자 계정 연결**: `Space.ownerId`를 실제 공간주에게 연결하는 UI가 없음(DB 직접 수정만 가능, 메모에 명시된 기존 갭). 공간을 10곳으로 늘리는 시나리오에서 이건 **매번 개발자가 손으로 처리해야 하는 병목**.

## 4. 추천 시스템

- **현재 철학**(취향 점수 기반, 같은 공간은 최신 점수만) 자체는 방향이 맞고 구현도 정확함(직전 세션에서 검증 완료).
- **부족한 데이터**: `ENABLE_RECORD_TAG_SELECTION=false`라서 태그 기반 보강 신호가 없음 — 순수하게 "방문한 공간의 관리자 태그 × 점수"만으로 벡터를 만듦. 파일럿처럼 공간 수가 적으면(10곳) 취향 벡터가 겹치는 태그가 거의 없어 추천이 자주 비어 보일 수 있음.
- **추천 기준**: 방문한 공간은 후보에서 제외하는 정책은 좋음. 다만 지역(district) 우선 필터가 있어 10곳이 여러 동네에 흩어져 있으면 "같은 지역" 후보가 0~1개뿐일 수 있음(코드는 이미 지역 확장 폴백을 갖고 있어 완전히 막히진 않음).
- **추천 설명**: "최근 높은 점수를 준 공간들과 '조용한' 결이 닮아 있어요" 같은 문구는 담백하고 좋음. 다만 매칭 태그가 하나도 없으면 "당신이 좋아한 공간들의 분위기와 가장 가까운 공간이에요"로 매우 일반화됨 — 초기 데이터 부족 구간에서 이 문구가 자주 나올 것.
- **추천 결과 UX**: 위 1번 섹션 지적대로 **방명록을 써야만 노출**되는 게 가장 큰 문제. 그 외엔 `/discover`, `/archive`에서도 상시 노출되므로 완전히 안 보이는 건 아님.

## 5. 방명록 (GuestbookSession → Post-it → Comment → Reaction → Notification → Archive)

- **너무 복잡한 부분**: 세션 개념(DRAFT/ACTIVE/ARCHIVED) + 방문 단위(recordId) + 군집(FREE/QUESTION_1/QUESTION_2)이 겹쳐 있어 개발 관점에선 정교하지만, 방문자 입장에선 "왜 예전 글이 안 보이지" 하나로 충분히 혼란스러울 수 있음(운영자에게도 마찬가지, 2번 섹션과 동일).
- **부족한 부분**: 댓글에 알림은 가지만, 알림 확인 통로가 `/archive`의 종 아이콘 하나뿐. 방명록을 쓴 뒤 다시 아카이브를 안 열면 반응을 영원히 모름.
- **실제 공간에서 생길 문제**: 포스트잇 색/충돌 방지는 화면에서만 의미 있음 — 실제로는 "내 흔적이 어디 있는지 찾기 어렵다"는 불만이 나올 수 있음(무한 캔버스 특성상). "내 기록 보기" 버튼이 있어 완화되지만, 처음 쓰는 사람은 이 버튼의 존재를 모를 수 있음.
- **악용 가능성**: 텍스트 콘텐츠(80자 이내)에 대한 욕설/광고 필터가 전혀 없음. 신고 기능도 없음(2번 섹션 지적과 동일 — 운영자 삭제 권한 없음). 실사용 시 가장 먼저 터질 리스크.
- **운영자가 불편할 부분**: 다음 회차로 넘어가면(ACTIVE→ARCHIVED) 이전 글은 읽기 전용이 되는데, 이 타이밍을 운영자가 직접 눌러 결정해야 함 — "언제 다음 방명록을 시작해야 하나"에 대한 가이드(예: 최소 기간 권장)가 없어 임의로 결정하게 됨.

## 6. 아카이브

- **계속 들어오고 싶을까?**: 취향 문구·태그 그래프·닮은 공간·닮은 사람·내가 남긴 흔적이 한 화면에 있어 "내 것"이라는 느낌은 강함. 다만 알림을 놓치면 다시 열 이유가 약해짐(5번 섹션과 연결).
- **부족한 부분**: 시간이 갈수록 쌓이는 "내가 남긴 흔적"은 가로 스크롤 한 줄로만 보여 N이 커지면 훑어보기 불편해질 수 있음(현재는 문제없지만 6개월 후 방문 20곳을 상상하면).
- **너무 많은 부분**: 현재는 과하지 않음 — 오히려 정보 밀도가 적절함.
- **시간이 지나면 필요할 기능**: "올해 다녀온 공간" 같은 연간 회고(레트로스펙티브)나, 계절/월별 묶어보기. 지금 구조(Record.visitedAt)로 나중에 충분히 만들 수 있는 확장이라 지금 만들 필요는 없음.

## 7. KPI

- **운영자가 실제 궁금할까?**: QR 이용자·재방문율·방명록 참여율·평균 취향 적합도는 실제로 궁금할 지표들. 잘 골랐음.
- **의미 없는 KPI**: **"방문자 취향 TOP3"가 구조적으로 거의 항상 비어있음**(`ENABLE_RECORD_TAG_SELECTION=false`라서 신규 기록엔 태그가 안 쌓임). 관리자 KPI 화면과 운영자 리포트 양쪽에 자리를 차지하고 있는데 실제로는 "데이터 없음"만 반복 노출 — 신뢰도를 깎는 요소.
- **부족한 KPI**: "평균 재방문까지 걸린 기간"(예: 며칠 만에 돌아오는지) 같은 리텐션 속도 지표가 없음. 지금은 재방문 여부(수/율)만 있고 "빠르게 돌아오는지 느리게 돌아오는지"는 안 보임 — `Record.visitedAt` 데이터로 계산 가능한 저비용 지표.

## 8. 다국어

- **번역 흐름**: 설계는 탄탄함(공간/에피소드/씬 단위 fallback, 언어 감지 우선순위). 다만 **OpenAI 키로 실제 생성 검증이 아직 안 됨** — 운영 투입 전 반드시 확인.
- **언어 선택**: 스위처가 공간 상세 페이지에만 있음. 에피소드 상세/기록/방명록/아카이브로 넘어가면 언어를 바꿀 UI 자체가 없음(쿠키로 유지는 되지만 전환 지점이 한 곳뿐).
- **Episode**: 제목/부제/본문은 번역되지만, 이전/다음 에피소드 링크의 제목은 원문(한국어)만 노출(스코프 아웃으로 이미 기록됨).
- **방명록**: **번역 대상이 전혀 아님.** UI 라벨("이 공간에 어떤 흔적을 남길까요?" 등)과 방문자가 남기는 글 모두 100% 한국어. 외국인 방문자가 공간 소개는 자기 언어로 읽다가, 정작 이 서비스의 정서적 핵심인 방명록에서 완전히 한국어 벽에 부딪힘 — **가장 몰입이 깨지는 지점**.
- **결론**: 번역은 "읽는 콘텐츠"에만 적용되고 "참여하는 UI"엔 전혀 적용 안 됨. 외국인 방문자 비중이 있는 공간(예: 홍대/연남 관광객 상권)이라면 이 갭이 바로 체감될 것.

## 9. MVP 범위 분류

**반드시 있어야 하는 것 (있으면 MVP 성립)**
- QR/Cube 진입, 방문 기록, 재방문 판정 — 있음
- Episode 잠금/해제 — 있음
- 방명록 작성/열람 — 있음(가장 완성도 높음)
- 최소 추천 로직 — 있음(데이터 적으면 약하지만 구조는 있음)
- 관리자 공간/콘텐츠 관리 — 있음
- 기본 KPI — 있음

**있으면 좋은 것 (MVP 이후)**
- 다국어 UI 전체 커버리지(현재는 콘텐츠만)
- 운영자 실제 알림 발송(이메일/문자)
- 취향 심화 데이터(태그 재도입 or 새 수집 UX)
- Waitlist 자동 알림
- 연간 회고 뷰

**하지 않는 것이 좋은 것**
- SNS 피드/팔로우/좋아요 랭킹 — 이미 정책상 "전체 인기 순위 페이지 금지"로 스스로 배제하고 있음, 유지 권장
- AI 기반 추천 고도화 — 지금 규모(10곳)에선 과함, 데이터도 부족
- 실시간 채팅/DM — 운영 부담·모더레이션 부담 급증, 철학과도 안 맞음
- 포인트/레벨/상점형 게이미피케이션 — "조용한 흔적"이라는 톤과 충돌
- 방명록 좋아요 랭킹/인기글 노출 — 이미 배제된 정책, 유지

## 10. 실제 운영 시나리오 — 망원 카페·독립서점·티룸·셀렉트샵 등 10곳, 운영 첫 달

- **사용자가 안 쓰는 이유**: 첫 방문은 언박싱 애니메이션+점수 매기기로 재미있지만, 두 번째 방문 시 Episode가 2~3개뿐이면 "이미 다 봤다"는 느낌 → 방명록만 남고 재방문 동기가 급격히 약해짐.
- **운영자가 안 쓰는 이유**: 월간 리포트가 자동으로 안 오고(수동 생성 버튼) 관심이 식으면 리포트 존재 자체를 잊음. 대시보드를 스스로 찾아와야 하는 구조는 "매달 확인하는 습관"을 만들기 어려움.
- **설치 후 발생 문제**: 10곳이 각자 다른 QR 인쇄 품질/위치로 붙이면 스캔 실패율 편차 발생. Cube 상태(UNASSIGNED/DISABLED)를 운영자가 인지 못 해 "왜 안 되냐"는 문의가 관리자에게 몰릴 수 있음.
- **콘텐츠 문제**: Episode 작성이 전부 수작업이라, 10곳 모두 최소 3개씩 채우려면 상당한 초기 공수. 공간마다 콘텐츠 퀄리티 편차가 클 것(운영자의 글쓰기 역량에 좌우).
- **데이터 문제**: 파일럿 규모(10곳)에서는 추천 후보 풀 자체가 좁아 "닮은 공간"이 자주 비거나 반복됨. KPI TOP3 취향은 계속 공백. 초반 몇 주는 모든 지표가 "샘플 부족" 상태일 가능성이 높음(`MIN_SAMPLE_QR_USERS` 임계값 미달).

## 11. 경쟁력

- **강점**: 리뷰/지도 서비스가 "정보 전달"에 집중하는 것과 달리, 공간큐브는 "공간과 나의 관계를 기록하는 의식"에 집중함. 언박싱 애니메이션, 무한 캔버스 방명록, 조용한 알림, 순위/랭킹 배제 — 이 디테일들이 실제로 철학(과시 아닌 기록)을 화면 곳곳에서 일관되게 전달함. 최근 세션들에서 방명록/추천/QR을 다듬으면서도 이 톤을 한 번도 깨지 않은 점이 인상적.
- **부족한 점**: 철학은 선명한데, 그 철학을 유지하려면 콘텐츠(Episode)가 계속 공급돼야 하고, 그건 100% 운영자의 손에 달려 있음. 즉 **철학의 유지 비용이 운영자에게 전가**돼 있음 — 서비스가 커질수록 이 병목이 먼저 드러날 것.

## 13. 특히 보고 싶었던 것 — 종합

- **빠진 연결**: 기록(비공개) ↔ 방명록(공개)이 텍스트 층위에서 하나로 뭉쳐 있음. 추천은 방명록에 종속. 신규 공간 생성 ↔ 방명록 세션 부트스트랩이 자동으로 안 이어짐. 월간 리포트 ↔ 운영자 알림이 끊겨 있음(생성은 되지만 전달이 안 됨).
- **UX 흐름에서 끊기는 부분**: "추천" 스텝(방명록 작성 필수), 언어 선택(공간 페이지 이후 전환 불가), 알림(아카이브를 열어야만 인지).
- **철학과 안 맞는 요소**: 현재는 발견되지 않음 — 오히려 철학이 코드 구석구석까지 일관되게 지켜지고 있는 편(순위 배제, 조용한 알림 등).
- **운영자가 겪을 문제**: 리포트 수동 생성/미발송, 콘텐츠 제작 부담, 방명록 통제권 없음, ownerId 수동 연결.
- **사용자가 재방문하지 않는 이유**: Episode 소진 후 재방문 동기 약화, 알림을 놓쳐 반응을 모름, 재방문해도 "새로 뭐가 생겼는지" 요약이 약함.
- **실제 서비스에 반드시 필요한 기능**: 기록 메모, 방명록 무관 추천 노출, 리포트 실제 발송. (12번 표의 P0 세 가지)

## 14. 최종 보고서

### 전체 완성도: **72 / 100**
핵심 경험(QR→공간→Episode→방명록)의 완성도와 톤 일관성은 90점대에 달할 만큼 뛰어나지만, 그 경험을 지속시키는 장치(알림 발송, 추천 노출 보장, 콘텐츠 공급, 운영자 리텐션)가 얇아 "한 달 이상 실제로 굴러가는 서비스"로서는 아직 절반쯤 와 있습니다.

### 가장 큰 장점 TOP 10
1. QR→언박싱→공간→Episode로 이어지는 도입부 연출의 완성도
2. 무한 캔버스 방명록의 충돌 방지 + 방문 단위 정책(최근 정교화 완료)
3. 추천 로직의 철학적 일관성("최신 취향만 반영")과 실제 구현 정확성
4. 순위/랭킹/좋아요 경쟁 요소를 의도적으로 배제한 절제된 톤
5. ownerId 기반 운영자/관리자 권한 분리(멀티테넌시 사고)
6. Cube 모델 기반 QR 계측 품질(스캔 출처·기기·언어까지 기록)
7. Episode 방문 횟수 잠금이라는 억지스럽지 않은 재방문 유도 장치
8. 조용한 알림 철학(실시간 폴링 없음, SNS 피드 지양)
9. 다국어 아키텍처의 설계 완성도(fallback 체인, 감지 우선순위)
10. 최근 리팩터링으로 더미데이터·죽은 코드·QR 이중체계가 정리된 코드 기반 위생 상태

### 가장 아쉬운 점 TOP 10
1. 기록 단계에 비공개 메모가 없어 "나만의 기록"이 텍스트로 안 남음
2. 추천 노출이 방명록 작성 여부에 종속됨
3. 월간 리포트가 운영자에게 자동 도달하지 않음(생성도 수동, 발송도 없음)
4. 알림이 아카이브 안 종 아이콘 하나에만 갇혀 있음
5. 방명록 콘텐츠에 대한 운영자 통제권(신고/숨김) 전무
6. KPI/리포트의 "취향 TOP3"가 구조적으로 거의 항상 공백
7. Episode 콘텐츠 제작이 100% 수작업이라 확장 시 병목
8. 다국어가 콘텐츠에만 적용되고 참여형 UI(방명록·기록)엔 전무
9. 아카이브 기록 상세 페이지가 사실상 빈 페이지(삭제 버튼 외 정보 없음)
10. 신규 공간 생성 시 방명록 세션 자동 부트스트랩 부재(관리자 수작업 의존)

### MVP 전에 반드시 해야 하는 것
- 기록 단계 비공개 메모 추가
- 기록만으로도 최소 추천 노출되도록 흐름 보강
- 월간 리포트 실제 발송(이메일 최소)
- 방명록 신고/운영자 숨김 최소 기능
- 신규 공간 생성 시 방명록 세션 자동 생성

### MVP 이후 해도 되는 것
- 다국어 UI 전체 커버리지 확대
- Waitlist 자동 알림
- 재방문 소요 기간 등 리텐션 속도 KPI
- 연간/계절 회고 뷰

### 하지 않는 것이 좋은 것
- SNS 피드/팔로우/좋아요 랭킹
- AI 기반 추천 고도화
- 실시간 채팅/DM
- 포인트·레벨·상점형 게이미피케이션

### 실제 운영에서 가장 먼저 생길 문제
방명록에 부적절한 글이 올라와도 운영자가 지울 수 없다는 것 — 오프라인 공간에 걸리는 콘텐츠에 대한 최소 통제권 부재는 설치 첫 달 안에 실제로 부딪힐 가능성이 가장 높은 문제입니다.

### 가장 기대되는 기능
무한 캔버스 방명록 + 방문 단위 정책. 사용자가 실제로 손으로 위치를 골라 흔적을 남긴다는 물리적 은유가, 이 서비스가 다른 리뷰/체크인 앱과 완전히 다른 정서를 만드는 지점입니다.

### 가장 과한 기능
`GuestbookSession`의 DRAFT/ACTIVE/ARCHIVED 3단계 상태 + 군집(FREE/QUESTION_1/QUESTION_2) 개념. 개발적으로는 정교하지만 방문자·운영자 양쪽 모두에게 "왜 예전 글이 안 보이는지" 같은 학습 비용을 요구합니다. 기능을 없애자는 게 아니라, 이 복잡도에 걸맞은 온보딩 설명이 아직 없다는 뜻입니다.

## 마지막 질문 — 내가 실제 공간 운영자라면, 돈을 내고 쓸 것인가?

### 답: **고민된다**

**이유**: 방문자가 겪는 핵심 경험(QR 언박싱 → 이야기 잠금해제 → 방명록)은 진심으로 매력적이고, 다른 어떤 리뷰/지도 서비스도 주지 못하는 "우리 가게만의 서사"를 만들어 줍니다. 이 부분만 보면 기꺼이 돈을 낼 이유가 있습니다.

하지만 실제로 매달 돈을 내는 결정을 내리려면 "이게 내 사업에 도움이 됐다"는 증거를 제가 스스로 찾아가야 하는데, 지금 구조에서는:
1. 월간 리포트가 제 손으로 눌러야 생기고, 제 이메일함으로 오지도 않습니다 — 관심이 한 번 식으면 그걸로 끝입니다.
2. Episode를 계속 채워 넣어야 이 서비스의 재방문 유도력이 유지되는데, 그 콘텐츠 제작 부담을 전부 제가 져야 합니다.
3. 방명록에 이상한 글이 올라와도 제가 지울 수 없어서, "내 가게에 걸리는 콘텐츠"에 대한 통제권이 없다는 불안이 남습니다.

이 세 가지(리포트 자동 도달, 콘텐츠 제작 부담 완화, 최소한의 통제권)가 해결되면 "고민된다"에서 "사용할 것"으로 바로 넘어갈 수 있는 서비스라고 판단합니다. 핵심 경험은 이미 돈값을 하는데, 그 가치를 운영자가 "계속 느끼게" 만드는 장치가 아직 따라오지 못한 상태입니다.
